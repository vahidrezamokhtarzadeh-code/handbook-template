# Fill Handbook — Staged Prompts

> This file is generated by `bootstrap-handbook.mjs` into a bootstrapped project.
> It is the staged prompt set an AI agent (e.g. Freebuff) should follow to fill the handbook.
> Do not edit this file by hand during a fill run; if you need to change the flow, change the
> generator (`bootstrap-handbook.mjs`) and re-run bootstrap, or document the deviation in
> `handbook-fill-plan.md`.

## How to use these stages

- Work through the stages in order. Later stages depend on earlier ones.
- Each stage is a separate prompt. Treat each stage as a bounded task with a clear output.
- After each stage, write a short note about what was filled, what is still placeholder, and what needs a human.
- Do not present inferred content as Accepted. If there is no real evidence, mark it Candidate / Needs-confirmation and say so.
- Cite evidence where it exists: file path, git ref, existing doc, PR, issue, conversation. If there is no source, say "no source — inferred."

## Mandatory rules for every stage

1. Do not invent Accepted decisions. A decision is Accepted only when there is real evidence.
2. Do not generalize one example into a platform rule unless a separate ADR explicitly does so.
3. Keep status tags honest: Accepted, Candidate, Deferred, Open Decision, Explicitly-not-modeled.
4. Keep DECISION-TRACE.md and PROJECT-NARRATIVE.md in sync with whatever you accept.
5. Keep CONTEXT-COVERAGE.md and the index files in sync with what you write.
6. If a file already has content, do not silently overwrite accepted content. Patch or append, and say what you changed.
7. After any decision or change, update the relevant doc(s) and the indexes. This rule is obligatory and lives in AGENTS.md.

## Inputs the agent should load first

1. `docs/PROJECT-COMPASS.md`
2. `docs/START-HERE.md`
3. `docs/project/runbooks/handbook-fill-plan.md`
4. `docs/project/runbooks/mining-package.json`

If the project has extra evidence available, load it too: README, CONTRIBUTING, existing ADRs, existing stories, chat exports, PR descriptions, issue text, manuscript files, notes, or anything else that describes what the project is for. The more real evidence the agent has, the less it has to infer.

## Project-type detection

Before filling, the agent should decide what kind of project this is, using the mining package and a quick scan of the repo.

- If `mining-package.json` already says `projectTypeHint`, start from that and verify it.
- If the project looks like a code repo, treat the code, configs, infra files, tests, and existing docs as the main evidence.
- If the project looks like a book/manuscript project, treat the manuscript files, outline, notes, and any existing front matter as the main evidence.
- If the project is mixed or unrecognized, say so explicitly and proceed cautiously.

Do not force a code-project shape onto a book project, and do not force a book shape onto a code project.

## Stage 0 — Load context and confirm scope

### Input
- mining-package.json
- handbook-fill-plan.md
- PROJECT-COMPASS.md
- START-HERE.md
- any available evidence bundle

### Output
- A short context summary:
  - what the project appears to be,
  - what kind of project it seems to be,
  - what evidence is available,
  - what is missing,
  - what the agent will infer versus what it found.

### Constraints
- Do not assume purpose from a single file.
- Do not invent a purpose if none is visible; say "purpose not yet established."
- Record the project-type judgment and why.

## Stage 1 — Fill the truth layer

Files:
- `docs/LATEST-STATE.md`
- `docs/DECISION-TRACE.md`
- `docs/PROJECT-NARRATIVE.md`

### LATEST-STATE.md

- Fill the Direction section with a plain-language one-paragraph description of what the system/project is, expressed in capabilities, not tool names, if evidence supports it.
- If there is no usable evidence, leave Direction as a clearly marked placeholder and say why.
- Fill the Deployment row only if deployment is visible:
  - for code projects: from Dockerfile, compose, k8s hints, deploy scripts, CI, or existing docs;
  - for book projects: from publishing path, format targets, distribution notes, or existing docs;
  - otherwise leave it as a marked placeholder.
- Fill the Technology table only from observed facts:
  - runtime/tooling from package.json, build files, imports, CI, etc.;
  - database/persistence from schema files, migration folders, data modeling docs, or references in code;
  - mark anything not visible as "not yet observed."
- Leave Accepted sections empty unless there are real decisions to record. Do not invent them.
- If there is existing history, summarize recent activity as observation only, not as decisions.
- Set Current Phase honestly:
  - fresh/near-empty: "fresh — no decisions captured yet"
  - existing with history but no captured decisions: "existing project, decisions not yet captured"
  - existing with captured decisions: reflect the actual phase.

### DECISION-TRACE.md

- Do not invent rows.
- If there are already decisions captured elsewhere, add rows that point at real evidence.
- If there are no decisions yet, leave the table empty and add a one-line note: "No decisions captured yet. Add a row whenever a decision is Accepted."
- If the project is existing and there is git history, you may surface candidate topics worth capturing, but mark them as "candidate, needs confirmation," not as decisions.

### PROJECT-NARRATIVE.md

- Add a "Why this file exists" note if helpful, but do not fabricate causal stories.
- If there are real decisions already made, write one "Why" section per decision with evidence.
- If there are no real decisions yet, leave the narrative skeleton and note that it is awaiting evidence.
- Never write a causal story that is not supported by something in the repo or evidence bundle.

## Stage 2 — Fill the handoff surface

Files:
- `docs/START-HERE.md`
- `docs/CONTEXT-COVERAGE.md`
- `docs/EXECUTABLE-DESIGN-INDEX.md`
- `docs/SOURCE-HANDOFF.md`

### START-HERE.md

- Keep the reading order.
- Fill the current phase honestly.
- Fill the current next action with one real sentence if possible; otherwise leave a marked placeholder.
- Add project-specific continuation rules only if there is a real basis for them.
- If the project is fresh, say so plainly.

### CONTEXT-COVERAGE.md

- Start from the existing table.
- Add rows only for discoveries that actually exist.
- If nothing has been discovered yet, keep the template table and add a note that discovery is not complete.
- Distinguish evidence from inference explicitly.

### EXECUTABLE-DESIGN-INDEX.md

- Keep the structure.
- Fill the "why" and "what is being built" pointers only if the corresponding files exist.
- If the project is fresh, leave the index as a skeleton pointing at the files that will exist later.

### SOURCE-HANDOFF.md

- Fill the source checkpoint only if there is a real source checkpoint.
- If there is no source yet, say so.
- Keep the caveats honest; do not invent caveats.

---

## Stage 3 — Fill first project body artifacts

This stage creates the first numbered artifacts from the templates and fills them with honest first drafts.

Do not create artifacts that have no basis whatsoever. If there is nothing to say yet, create the skeleton and mark it as awaiting evidence.

### Stories

- Create the first story file from `docs/project/stories/_TEMPLATE.md` if there is a real use-case or behavior to record.
- If there is no real story yet, do not invent one. Leave a note in the folder or in the fill summary.
- A story is evidence, not a universal template.

### Decisions

- Create the first ADR file from `docs/project/decisions/ADR-001-template.md` only if there is a real decision to record.
- If there are no real decisions yet, do not create ADR-001 as if it were real. Instead, leave a placeholder ADR skeleton if desired and mark it as not yet meaningful.
- Update `docs/project/decisions/DECISION-INDEX.md` to reflect what exists.

### Domain

- Create the first domain concept file from `docs/project/domain/_TEMPLATE.md` only if there is a confirmed or candidate concept worth recording.
- If there is no domain content yet, leave the folder skeleton.

### Architecture

- Create the first architecture doc from `docs/project/architecture/_TEMPLATE.md` only if there is a boundary/flow/contract worth defining.
- If there is none yet, leave the folder skeleton.

### Technology

- Create the first technology decision file from `docs/project/technology/_TEMPLATE.md` only if there is a real tool/implementation choice to record.
- Prefer observed facts from the repo; do not invent technology decisions.

### Data model

- Create the first data-model doc from `docs/project/data-model/_TEMPLATE-logical-schema.md` only if there is a persistence concern worth modeling.
- If there is a schema file already, reference it. If not, leave a skeleton.

### Contracts

- Create the first contract schema only if there is a real machine-readable contract to define.
- Otherwise leave the contracts folder with its README.

### Open decisions

- Create the first open-decision file from `docs/project/open-decisions/_TEMPLATE.md` only if there is a real unresolved question worth tracking.
- If there are none yet, leave the folder skeleton.

## Stage 4 — Fill implementation and runbook skeletons

Files:
- `docs/project/implementation/implementation-plan.md`
- `docs/project/implementation/test-matrix.md`
- `docs/project/implementation/remaining-technical-gates.md`
- `docs/project/runbooks/new-chat-continuation.md`

### implementation-plan.md

- Fill only what is real:
  - if the project has an existing plan or obvious first slice, reflect it;
  - otherwise leave the phase skeleton and note that the plan is not yet established.
- Do not invent phases or deliverables out of thin air.

### test-matrix.md

- Add rows only for invariants that exist or are being introduced.
- If there are no invariants yet, leave the table skeleton.

### remaining-technical-gates.md

- Fill only if there are real gates.
- If there are none yet, leave the skeleton and note that.

### new-chat-continuation.md

- Keep the handoff sequence.
- Fill current snapshot and reasoning checkpoints only if they are real.
- If the project is fresh, say that the continuation notes are awaiting real content.

## Stage 5 — Close the loop

### Update indexes
- `docs/project/decisions/DECISION-INDEX.md`
- `docs/CHANGELOG.md` if the snapshot changed

### Write the fill summary
Write or update:
- `docs/project/runbooks/fill-summary.md`

The summary should say:
- what the agent filled in this run,
- what it inferred versus what it found in the repo,
- what it deliberately left as placeholder,
- what needs a human to confirm,
- what was already present before this run.

### Update PROJECT-COMPASS.md if needed
- If the truth layer changed materially, update the compass so it stays a true synthesis.
- If the compass would become long, move detail back into the files it summarizes.

---

## Optional orientation stage — PROJECT-COMPASS.md

This stage is optional. Run it only if a short synthesized orientation is useful.

- PROJECT-COMPASS.md should be a true synthesis of LATEST-STATE.md, PROJECT-NARRATIVE.md, DECISION-TRACE.md, and the implementation plan.
- It should answer four questions:
  - what is this project about?
  - where is it leading?
  - what is the next step?
  - how do I reach it?
- It should stay short. If it grows long, fold the detail back into the files it summarizes.
- If it conflicts with a detailed file, the detailed file is more authoritative.

---

## End-of-run rule

Before finishing, the agent should confirm:

- No Accepted decision was invented.
- Every inferred claim is marked Candidate/Needs-confirmation or otherwise flagged.
- Every index that should have changed was updated.
- The fill summary exists and is honest.
- AGENTS.md's mandatory doc-update rule is still intact.

If any of those is false, fix it or say explicitly what is wrong and why.
